## Detail and recommended fixes

### S1 — Fail-open sync authentication (HIGH)

```ts
// resolve-request-auth.ts
const syncAuthorized =
  syncToken === undefined ||
  syncToken === '' ||
  userId !== null ||
  (bearer !== null && bearer === syncToken);
```

If `SNIFFOUT_SYNC_TOKEN` is ever missing or empty in production, **`syncAuthorized` is `true` for every caller** — `scans.sync` becomes an open write endpoint (anyone can inject scan/consent records). This is the opposite of `apps/web/src/lib/db.ts`, which correctly _throws_ when `DATABASE_URL` is absent under Vercel/production. The auth layer has no equivalent fail-closed guard, even though the spec (§8.2) states: _"Production: `SNIFFOUT_SYNC_TOKEN` must be set; unauthenticated sync rejected."_

**Fix:** In production (`VERCEL`/`NODE_ENV==='production'`), if no valid JWT and `syncToken` is unset/empty → `syncAuthorized: false` (and log a startup error). Only allow the open path in dev.

### S2 — Public read of all tenant scan data (HIGH)

`scans.list`, `scans.getDetail`, `scans.diff`, `hosts.list`, `findings.list` are all `publicProcedure`. I confirmed this against **live production**: an unauthenticated `GET /api/trpc/scans.list` returned real records (host IPs, targets, timestamps). For a product whose data _is_ customer network topology and vulnerabilities, this is a meaningful exposure. The spec footnote (§8.1) allows list/detail/diff to be public "in v1… lock down before G6," and already marks `hosts`/`findings` as **protected** — but the code ships them public and there is no regression test or tracking item.

**Fix:** (1) Make `hosts.list`/`findings.list` `protected` now (matches spec). (2) Add a pre-ship checklist item + a test asserting these reject unauthenticated calls once auth lands. (3) Until Phase 4, add at minimum a rate limit + a note that the deployment is single-tenant.

### E1 — Scope guardrails not implemented (HIGH, spec-required)

Spec §6.5 requires, _"before the first scan button works,"_ six guardrails. Only #1–2 (consent text + immutable storage) exist. **Missing:** #3 default max CIDR `/16` with confirmation, #4 max job size (65536 ports × 256 hosts) modal, #5 private/reserved-range block-unless-overridden. Neither `App.tsx`, `run-scan.ts`, nor the Rust command validate target scope. Consent is enforced (button disabled until checked; re-checked in `handleScan`), but a user can type `0.0.0.0/0` and run it.

**Fix:** Add a target-validation module (shared TS in `scan-engine`, re-checked in Rust) enforcing CIDR size, RFC1918/reserved handling, and job-size caps; block or require explicit override before dispatch. Treat as a **G2 re-certification** item.

### S4 — nmap argument injection at the privilege boundary (MED–HIGH)

```rust
// lib.rs build_nmap_args(): targets pushed raw, after -sV -oX -
args.push(targets.to_string());
```

`Command::new(nmap).args(&args)` avoids _shell_ injection (good — no shell string). But `targets` is an unvalidated user string passed as an nmap argument with **no `--` option terminator**. A value like `--script=<dangerous-nse> 127.0.0.1` or `-oN C:\path\file` is parsed by nmap as **flags**, enabling NSE script execution or file writes — precisely the "no exploit execution" line the product advertises. The guardrails live in TS/UI; the actual privilege boundary (Rust spawning a scanner) trusts the renderer completely.

**Fix:** Validate `targets` in Rust against an IP/CIDR/hostname allowlist and reject anything starting with `-`; insert a literal `"--"` before targets so nmap stops option parsing. Defense in depth even after E1 is fixed in TS.

### S3 / S5 — Token handling (MED)

- **S3:** `bearer === syncToken` is not constant-time. Use a length-checked, constant-time comparison (`crypto.timingSafeEqual`).
- **S5:** `VITE_SYNC_TOKEN` is embedded at build time, so every distributed desktop binary contains the same bearer secret — trivially extracted from the bundle, and shared across all installs. Acceptable for a single-tenant WORKSTATION deployment; a blocker for commercial multi-customer shipping. Resolve with per-user Supabase JWT (Phase 4) and stop shipping a shared write token.

### C1 / C2 — CVE correlation precision (MED)

- **C1:** `versionInRange` compares versions as strings (`version < start`). Lexicographically `"9" > "10"` and `"1.9" > "1.10"`, so real version ranges mis-match (both false positives and false negatives). Use a semver-aware comparator (and, once on NVD 2.0, prefer CPE `versionStartIncluding`/`versionEndExcluding` match logic).
- **C2:** `productMatches` returns true if _either_ string contains the other. Short product tokens produce false positives (`"ssh".includes("sh")`). Prefer exact/tokenized product+vendor matching (ideally CPE-based) to protect scanner trust.

### C3 — Silent fixture fallback masquerading as a real scan (MED)

In `run-scan.ts`, if `invoke('run_nmap')` throws for any reason, the catch block substitutes `get_fixture_nmap_xml()` and the run still completes and persists as `status: 'completed'`. A failed _authorized_ scan therefore yields the lab fixture (3 synthetic hosts incl. a fake Log4j finding) stored as if real. **Fix:** surface the failure (or require an explicit "fall back to fixture" choice) and tag provenance (`source: 'fixture' | 'live'`) on the scan run so fixture data can never be mistaken for findings.

### C4 / C5 — Data-model round-trip gaps (LOW–MED)

- **C4:** The `findings` table has no `port` column; `scans.sync` always writes `serviceId: null`; `loadScanDetail` sets `port: undefined`. So `Finding.port` (in the domain type and used by the diff key and host-detail UI) never survives a cloud round-trip — diff keys collapse to empty port, weakening `scans.diff`. Add a `port` column (or an enforced `service_id` link) and populate it.
- **C5:** `parse-xml` assigns the nmap `service @_name` (e.g. `"http"`) into `Service.banner`. The field is mislabeled and the real banner is never captured. Rename/repurpose.

### D1 / D2 / D3 — Database (MED / MED / LOW)

- **D1:** Migration `0000_modern_zodiak.sql` has 15 `CREATE TABLE` and **zero** `CREATE INDEX`. Every FK lookup (`hosts.scan_run_id`, `services.host_id`, `findings.scan_run_id`, `findings.host_id`) and the `scan_runs.started_at DESC` ordering used by `scans.list` are unindexed. This contradicts the repo's own bundled skill `.agents/skills/supabase-postgres-best-practices` (schema-foreign-key-indexes, query-missing-indexes). Add FK + `started_at` indexes in a new migration.
- **D2:** `hosts`, `services`, `findings` carry no `org_id` (only `scan_runs` does, nullable). Phase-6 ADMIN RLS scoping rows by `org_id` will require either denormalizing `org_id` onto leaf tables or join-based policies — decide now to avoid a large backfill migration later.
- **D3:** The app-managed `users` table will duplicate Supabase `auth.users`. Phase 4 must define which is source of truth and the `auth.uid → users.id` mapping.

### P1–P4 — CI / delivery (MED / MED / LOW / LOW)

- **P1:** The `boundaries` job only runs `lint` on `@sniffoutpro/config` + `@sniffoutpro/types`; it does not execute `eslint-plugin-boundaries` across `apps/*`. The ADR-001/§3.3 claim that `apps → packages`-only is "enforced in CI" is currently not true. Wire the boundaries rule into the app ESLint configs and run it.
- **P2:** No Rust job in CI. `cargo test`, `cargo clippy -D warnings`, `cargo fmt --check` should run — the nmap spawner is the highest-risk code and is currently unguarded by CI.
- **P3:** `deploy.yml` runs verify → migrate → deploy but has no **post-deploy smoke** step; `scripts/verify-production.mjs` exists but isn't invoked. Add it as a gate so a bad deploy (like the ENOTFOUND episode) fails the pipeline automatically.
- **P4:** Enforce coverage thresholds in CI (line ≥85% **and** branch ≥80%; branch was ~70% per PHASE-LOG) and run Playwright in CI (currently only `typecheck lint test`).

### R1 — react-force-graph on the web (MED)

`react-force-graph-2d` accesses `window` at module evaluation, causing `ReferenceError: window is not defined` under Next SSR/prerender, and it declares React ≤18 peers (conflict under React 19). The **desktop** app already lazy-loads it client-side (fine). The **web** `/dashboard` must dynamic-import it with `ssr: false` and pin a peer override/resolution, or the Next build/prerender can break. Verify `dashboard-client.tsx` does this.

### SP1 / SP2 — Spec currency & doc drift

- **SP1:** §10 says "Fetch NVD JSON feeds." NIST is retiring the legacy data feeds in favor of the **NVD 2.0 REST API** (1.0 API already retired; feeds on borrowed time). The CVE-sync job should use the 2.0 API with an API key, incremental `lastModStartDate`/`lastModEndDate` windows (≤120 days), and rate-limit backoff.
- **SP2:** ADR-002/003 reference "embedded LibSQL/SQLite"; the implementation and §7.2 use **sql.js**. Align the ADR wording.

## What is solid (keep doing this)

Clean monorepo with real boundaries; `neverthrow` `Result` types through the engine; Zod at the API edge **and** re-parse on read; lazy DB singleton with a correct production fail-closed guard (`db.ts`); `postgres({ max: 1, prepare: false })` — exactly right for the Supabase transaction pooler; superjson transformer; discriminated-union progress events; immutable `authorization_scopes`; idempotent sync on `scanRun.id`; fixture-only CI (no live nmap); gitleaks + `pnpm audit` in CI; detection-only posture with a visible "no exploit execution" footer. This is a well-architected codebase — the findings above are hardening and precision, not structural rework.

## Recommended fix order (when you greenlight building)

1. **S1** fail-closed sync auth (small, highest risk).
2. **S2** protect `hosts`/`findings`, add lockdown test + rate limit.
3. **E1 + S4** target-scope guardrails in TS and re-validated in Rust (`--` terminator).
4. **D1** index migration; **P1/P2** boundaries + Rust in CI.
5. **C1/C2/C3** correlation precision + fixture provenance.
6. **C4/C5/D2/D3** data-model round-trip + RLS-readiness.
7. **P3/P4/R1** smoke gate, coverage thresholds, web graph SSR guard.
